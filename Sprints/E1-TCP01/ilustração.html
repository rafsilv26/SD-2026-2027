The TCP01 server takes clients in a while (true) loop around accept(). On the left, every accepted connection gets its own Connection object, holding its socket and streams and running on a separate thread. On the right, the same server without Connection: the request is handled inside the loop itself, and the next clients are left pending.

What the illustration shows

    
Establishing the connection

    
new Socket("localhost", 7896) on the client triggers the TCP three-way handshake (SYN, SYN-ACK, ACK). The operating system does this on its own: the server's accept() takes no part in it. That is why the handshake takes the same time in both scenarios, and why a connection can be fully established while nobody is accepting it yet.

    
One Connection object per request

    
Each new Connection(clientSocket) creates a new object that keeps that client's Socket and its two streams (in and out). Since each thread has its own object, requests share no state. The constructor still runs on the main thread; only this.start() creates the new thread, which executes run(). If run() were called directly, the code would run on main and behave like the right-hand panel.

    
Why the request is pending rather than refused

    
Once established, the connection sits in the ServerSocket queue (the backlog) until someone calls accept(). The client's new Socket(...) returns, and so does its writeUTF(), because the bytes land in the server's buffer. The client then blocks in readUTF() until main finishes the previous request and picks up the connection.

    
The price of threads

    
With threads, the number of live threads follows the number of connected clients and drops back to 1 once they all finish. Each thread costs memory and scheduling time, which is the limitation raised in CA5 for ten thousand simultaneous clients.
